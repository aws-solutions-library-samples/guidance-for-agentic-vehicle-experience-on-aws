# THIS FILE IS THE ONE THAT SHIPS. It is the only requirements file the
# AgentCore runtime installs from, for both the bidi and text runtimes.
#
# This file lives at the repo root because the AgentCore starter toolkit
# auto-detects `requirements.txt` relative to the source_path, and our
# source_path is the repo root (so the entrypoint can import the
# agents.supervisor.* package tree). `.bedrock_agentcore.yaml` contains no
# `requirements` key for either runtime, so there is no override.
#
# A sibling `agents/supervisor/requirements.txt` used to exist, and a comment
# here used to designate that sibling as the authoritative one, to be synced by
# hand. That designation was false and it caused a production outage:
# `redis==5.3.1` was declared there, agentcore bundled THIS file which lacked it,
# and the runtime could not initialize because the tools package imports redis at
# module scope (issues/2026-09-10-agentcore-runtime-missing-redis/). The same
# two-file confusion muddied the 2026-09-11 bidi diagnosis eleven days later.
#
# That sibling was DELETED 2026-09-21. Do not recreate it — declaring a runtime
# dependency anywhere but this file means it does not ship.
# tests/architecture/test_requirements_pins_repo_wide.py enforces its absence.
#
# Lambdas have their own requirements.txt under lambdas/*/ and are
# deployed by a separate build script (scripts/build-*.sh), so they
# are unaffected by this file.

# bedrock-agentcore-starter-toolkit: deliberately NOT listed here.
#
# It is the local `agentcore` CLI (deploy/invoke/configure), not a runtime import.
# Nothing in this repo imports `bedrock_agentcore_starter_toolkit` — verified
# 2026-09-21 — and the Makefile installs it standalone
# (`pipx install bedrock-agentcore-starter-toolkit`, Makefile:65 and :176), which

# It was pinned here on 2026-08-03 as `==0.3.9`, and that BLOCKED EVERY RUNTIME
# DEPLOY: 0.3.9 requires `openapi-spec-validator>=0.7.2`, while this file pins

#

# reconcile it against the openapi-spec-validator pin first — and note that
# bumping that pin is owned by spec 2026-09-18-avx-tier2-ios-cards-and-actions

# ── JWT signature verification at the bidi session boundary ───────────────────
# Used by agents/supervisor/jwt_verify.py (Fix Group 18 T18.6, security review
# Cycle 1 W1). bidi_app.py calls assert_jwt_enforceable() at import, so in
# `enforce` mode a missing package here refuses container start by design.
#
# Both of these ALREADY reach the image today — but only down a three-link chain
# of ranges that nothing in this repo controls, verified 2026-09-23 by reading
# installed distribution metadata:
#
#   strands-agents==1.48.0 -> mcp>=1.23.0,<2.0.0 -> pyjwt[crypto]>=2.10.1
#                                                      -> cryptography>=3.4.0
#
# So the hazard is not absence, it is drift — the same shape as the
# aws_sdk_bedrock_runtime incident above, three times over, since a rebuild may
# float mcp, PyJWT and cryptography independently. The load-bearing link is
# `mcp` requesting the `[crypto]` extra: that is a third-party decision a minor
# mcp release inside <2.0.0 could drop, which would silently remove RS256 from
# the image without changing one line of this repo. In `observe` mode that
# degrades quietly, which is the worst case for a security control.
#
# Declared explicitly for the reason the file header gives: a runtime dependency
# declared anywhere but this file does not ship. The `[crypto]` extra is stated
# on our own line to make the intent ours rather than inherited; the separate
# cryptography pin is what actually fixes the version, since the extra alone
# would leave it a range.
#
# Versions are the installed, locally-verified ones rather than latest (PyJWT
# 2.14.0, cryptography 50.0.1), per this repo's precedent of pinning known-good
# and treating an upgrade as its own decision. Quarantine per
# ~/.kiro/steering/dependency-versions.md is satisfied with wide margin:
# PyJWT 2.12.1 released 2026-03-13 (194d), cryptography 48.0.0 2026-05-04 (142d).
# Before changing either, run tests/architecture/test_bidi_runtime_deps_pinned.py.
PyJWT[crypto]==2.12.1
cryptography==48.0.0

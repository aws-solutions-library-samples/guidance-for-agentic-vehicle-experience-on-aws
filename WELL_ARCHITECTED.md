# Well-Architected Framework: Agentic Vehicle Experience on AWS

This document describes how the Agentic Vehicle Experience (AVX) Guidance aligns with the AWS Well-Architected Framework. The v1 Guidance covers the runbook-required minimum of three pillars — **Security**, **Cost Optimization**, and **Operational Excellence** — the three pillars where AVX's design choices most directly differ from a generic Bedrock agent deployment. The remaining two pillars (Reliability, Performance Efficiency) are covered by the AWS service defaults AVX inherits (AgentCore Runtime managed scaling, Bedrock regional endpoints, S3 durability); no AVX-specific design intervention is required for them at the v1 scale.

## Security

### What service(s) are you using to enhance security?

This Guidance uses AWS IAM, Amazon Bedrock AgentCore Identity, Amazon Bedrock Guardrails, Amazon Cognito, AWS KMS, AWS Lake Formation (v4 cross-account share), and CloudFront-fronted browser XSS defenses for security. IAM enforces least-privilege on the AgentCore execution role via resource-scoped statements: `BedrockModelInvocation` is scoped to the specific Sonnet 4.6 inference-profile ARN and the Nova Sonic v2 foundation-model ARN in `us-east-1` (no wildcards); `ApplyGuardrailScoped` is scoped to a single guardrail ARN in prod (`arn:aws:bedrock:us-east-1:${account}:guardrail/o1skd021xxnm`). AgentCore Identity provides the runtime with an execution identity distinct from any caller identity, and manages OAuth token vaulting for integrations with external identity providers. Bedrock Guardrails (prod deployments only) applies the `vsa-vehicle-scope` guardrail to Sonnet 4.6 output to prevent off-topic drift and PII exposure. Cognito authorizers validate every `/assistant/chat` request against a pre-trusted user pool (`EXTRA_USER_POOL_IDS`) and inject verified claims into the route Lambda context so the persona is inferred **server-side** from `cognito:groups` and `custom:role`, never trusted from the client payload. KMS provides per-stage customer-managed keys for AgentCore Memory storage, S3 Athena results, and cross-service decrypt operations. Lake Formation v4 cross-account share governs which ADP Glue databases the AVX AgentCore execution role can query cross-region. Browser output flows through an attribute-stripping `sanitizeHtml` allowlist (13 vitest cases) before rendering in the CMS web UI's `ChatAgent.tsx`, mitigating XSS from LLM-generated markup.

### How do these services help the user with security?

These services implement defense-in-depth across the request path from browser to model to grounding data. The Cognito authorizer + server-side `map_persona_from_claims()` pattern in [`lambdas/api-assistant-chat/persona_map.py`](./lambdas/api-assistant-chat/persona_map.py) prevents privilege escalation via client-controlled persona parameters — a browser cannot request the `service_advisor` persona if the operator's JWT claims are `fleet-operator`. AgentCore Identity separates the runtime's identity from the caller's, so tool-side IAM (Bedrock, Athena, KB Retrieve, DynamoDB writes) is bounded by the runtime role's permissions and cannot be widened by any caller. Bedrock Guardrails' region-scoped ARN configuration keeps guardrail policy versioned and centrally curated in one region (`us-east-1`), and the two-statement IAM split (`BedrockModelInvocation` + `ApplyGuardrailScoped`) intentionally preserves guardrail action-resource alignment — `bedrock:ApplyGuardrail` is granted only against the specific guardrail resource, and `bedrock:InvokeModel`/`InvokeModelWithResponseStream` are granted only against the specific model/inference-profile ARNs. Lake Formation v4's cross-account grant means AVX's AgentCore execution role has data-access to ADP Glue tables only via LF-issued temporary credentials — the AVX role does not hold long-lived S3 read on ADP's data lake, so a misconfigured AVX IAM policy cannot bypass ADP's row/column-level filters. KMS-managed keys ensure AgentCore Memory records are encrypted at rest with keys the AVX account controls, and per-service key policies (Bedrock, DynamoDB, S3) allow independent rotation without operational coupling. The XSS `sanitizeHtml` allowlist on the browser side is defense-in-depth against grounded-but-unsafe LLM output — even if the model synthesizes markup that includes a script tag, the attribute-stripping sanitizer removes it before render.

### Why are you using these services to support security?

We selected these services to enforce security invariants at the boundary layers (auth, IAM, guardrails, sanitizer) where a single misconfiguration cannot silently degrade the whole system, and to avoid the anti-patterns that specifically bit prior iterations of this stack. The two-statement IAM design (`BedrockModelInvocation` scoped to specific inference-profile ARNs, `ApplyGuardrailScoped` scoped to a single guardrail ARN) was chosen after an earlier dead-end where granting `bedrock:ApplyGuardrail` alone (without the InvokeModel actions on the same statement or with wildcard resources) degraded the session — resource-scoped and action-scoped statements avoid both privilege creep and the accidental-broadening that wildcards produce. The server-side persona inference pattern was chosen because AVX exposes six personas of varying data-access breadth (`fleet_driver` sees fleet KPIs; `service_advisor` sees KB `TSB/policy/manual`; `technician` sees KB `DTC/parts/SOP`) — trusting a browser-supplied `personaId` would have made AVX a privilege-escalation vector for any CMS pool user. AgentCore Identity's built-in token vault was selected over rolling a bespoke OAuth flow so that identity-provider tokens (for future retail-advisor integrations with dealership systems) can be delegated safely without long-lived tokens ending up in Lambda environment variables. Lake Formation v4 was chosen for cross-account data governance over per-table S3 bucket policies because LF's row/column-level enforcement applies to every ADP query path (Athena, Glue ETL, cross-account Bedrock KB) without requiring AVX to re-implement filtering client-side. Together, these services create a system where every hop in the request path validates identity and scope at the boundary, so no single tool factory or Lambda handler needs to re-implement authorization logic — and the choices in `vsa-core-stack.ts` are traceable to the persona-mapping and IAM design captured in [`docs/persona-mapping.md`](./docs/persona-mapping.md) and [`docs/runbooks/avx-cross-account-iam.md`](./docs/runbooks/avx-cross-account-iam.md).

## Cost Optimization

### What service(s) are you using to enhance cost optimization?

This Guidance uses serverless services (AWS Lambda, Amazon API Gateway, Amazon Bedrock AgentCore Runtime), usage-based Bedrock model invocation (Claude Sonnet 4.6 via cross-region inference profile + Nova Sonic v2 bidi), AgentCore Memory with 15-minute TTL + lazy-refresh, cross-region Athena with partition-scoped scans, and the tiered evals pipeline (`evals/runner/`) for cost optimization. Lambda and API Gateway bill per invocation with no idle capacity charge. AgentCore Runtime bills per invocation on vCPU-second and memory-GB-second granularity, so both the text runtime (`vsa_supervisor_text_staging`) and the bidi runtime (`vsa_supervisor_bidi_staging`) scale to zero between requests. Bedrock Sonnet 4.6 and Nova Sonic v2 are billed per input+output token / per audio minute — no committed capacity. AgentCore Memory persists session state for the session lifetime with a 15-minute TTL + lazy-refresh window, so repeated tool queries within a session hit the local memory record instead of re-issuing the cross-region Athena query. Athena's per-query pricing (charged only on data scanned) rewards the `persona_loader.load_persona`'s partition-scoped queries (10–20 MB per query, ~10–15 queries per session-init). The three-tier evals pipeline runs the free tiers first (Tier 1 tool-unit at $0/run + Tier 2 mocked-Nova conversation at $0/run) and only invokes the paid Tier 3 (real AgentCore E2E at ~$1/run) when the free tiers pass — so regressions are caught cheaply before any Bedrock token is spent.

### How do these services help the user with cost optimization?

These services align costs directly with actual usage and eliminate the dominant sources of cloud waste for AI-agent workloads. The serverless proxy layer (Lambda + API Gateway) contributes trivially to the monthly bill even at staging load — a demo deployment of the request path incurs no idle infrastructure cost during off-hours. AgentCore Runtime's per-invocation billing means the AVX text and bidi runtimes cost nothing when no user is chatting; there is no equivalent of a 24/7 EC2 instance or Fargate task to pay for. Bedrock's usage-based pricing means AVX pays for Sonnet 4.6 only on token throughput and Nova Sonic only on voice-minutes streamed — a demo deployment with occasional UAT costs far less than a production deployment with continuous fleet-driver voice traffic, and the cost curve tracks the customer-value curve. AgentCore Memory's 15-minute TTL + lazy-refresh window means a multi-turn session pays the ~$0.001–$0.003 Athena scan cost of session-init once, not once per turn — the second and every subsequent turn in a session reads from Memory, not from Athena. The Tier 1/Tier 2 free-first evals pattern is a cost lever specific to Bedrock workloads: because Tier 3 real-Bedrock evals cost ~$1/run and the free tiers detect 90%+ of regressions in <2 seconds each, AVX's CI pays cents per regression instead of dollars. Bedrock Guardrails in staging is intentionally not enabled — a curated guardrail in `us-west-2` has ongoing curation cost and would false-positive on dev-iteration queries; skipping guardrails in staging is an intentional cost + operational-noise tradeoff that reverses cleanly when real customer traffic reaches the environment. For a monthly cost projection tuned to your expected traffic, model each of the four cost centres (Lambda + API Gateway; AgentCore Runtime vCPU-second and memory-GB-second; Bedrock token/audio-minute usage; Athena scan bytes) against the [AWS Pricing Calculator](https://calculator.aws/); the Bedrock model card and AgentCore documentation give current per-unit prices in your region.

### Why are you using these services to support cost optimization?

We selected these services to keep the AVX bill proportional to real user activity, with no fixed floor for a demo deployment beyond a few dollars of CloudWatch and KMS. Serverless AgentCore Runtime was chosen over the alternative (ECS Fargate hosting a long-running agent container) because the request pattern for a chat/voice assistant is bursty by nature — a Fargate task sized for peak fleet-driver voice load would sit idle for 90%+ of the day. AgentCore Runtime's scale-to-zero property eliminates that idle cost entirely. AgentCore Memory was chosen over an alternative caching layer (ElastiCache Redis, DynamoDB with TTL) because Memory's storage + operations model is billed at a fraction of a provisioned Redis node and requires no capacity planning; the 15-minute TTL was tuned to match the ~8-min average voice session length so most sessions hit cache once per session-init and never re-scan Athena within the session. Athena was chosen over the alternative (materializing ADP tables into a AVX-owned RDS or Redshift cluster) because per-query pricing on partition-scoped scans is dramatically cheaper than any always-on cluster at AVX's staging scale (~$1.50/month for 300 GB scanned vs. hundreds of dollars/month for a small Aurora cluster). The tiered evals pipeline was chosen over the alternative (Bedrock-live evals on every PR) because Bedrock token costs on every PR would have made the eval budget the single largest AVX line item — routing 90% of regression detection through free-tier evals reduces regression-check cost by ~100×. Together, these choices make the AVX cost curve linear in customer usage rather than in deployed capacity, so the cost story scales cleanly from a single-account staging demo to a multi-tenant customer deployment without an architectural rewrite. Cost transparency to the operator is best re-derived per deployment using the [AWS Pricing Calculator](https://calculator.aws/) against the four cost centres named above (Lambda + API Gateway; AgentCore Runtime; Bedrock model + guardrail usage; Athena scan bytes); this separates fixed / usage-dependent / variable line items so the two dominant cost drivers (Bedrock Sonnet 4.6 token volume + Nova Sonic voice-minutes) are visible before any deploy commitment.

## Operational Excellence

### What service(s) are you using to enhance operational excellence?

This Guidance uses AWS CloudFormation (via CDK), Amazon CloudWatch (including Transaction Search), AWS X-Ray, the tiered evals pipeline (`evals/runner/tier1_tools.py`, `tier2_conversation.py`, `tier3_e2e.py`), an eight-script deploy-time smoke test suite (`scripts/smoke-test-*.py`), and a GitHub Actions auto-deploy workflow (`.github/workflows/evals.yml`) for operational excellence. CloudFormation via CDK (`infrastructure/lib/vsa-core-stack.ts`, `vsa-triage-classifier-stack.ts`, `vsa-api-stack.ts`) provisions the three-stack AVX topology consistently across staging and prod. CloudWatch aggregates logs from AgentCore Runtime, Lambda handlers, and Nova Sonic inference into a centralized surface, and CloudWatch Transaction Search (one-time-enable per account) makes cross-service request traces searchable by session ID. X-Ray traces distributed requests through the AgentCore runtime container's tool dispatch and cross-region Bedrock/Athena/KB calls. The tiered evals pipeline enforces regression detection at three fidelity levels — Tier 1 tool-unit evals in <2s, Tier 2 mocked-Nova conversation evals in <2s, Tier 3 real AgentCore end-to-end evals in ~10min — and every push to `main` runs the full tier-gated eval sequence before the `deploy-staging` job is even invoked. The eight-script smoke test suite (`smoke-test-agentcore.py`, `smoke-test-voice.py`, `smoke-test-voice-multiturn.py`, `smoke-test-kb-retrieve.py`, `smoke-test-assistant-chat.py`, `smoke-test-cross-account.py`, `load_persona_smoke.py`, per-persona Tier-3 audio smoke) validates each grounding surface post-deploy and fails the deploy pipeline if any surface is broken. The GitHub Actions workflow deploys via OIDC (no long-lived credentials in CI), gated on Tier 1/2/3 eval passes.

### How do these services help the user with operational excellence?

These services make AVX both **safe to deploy on every green PR** and **fast to diagnose when a regression slips through**. The three-tier eval pipeline catches 90%+ of regressions in the two free tiers before any Bedrock token is spent — Tier 1 catches individual tool-factory regressions in isolation (24 cases against a `evals/baselines/tier1.json` baseline), Tier 2 catches tool-routing and conversation-flow regressions using a mocked Bedrock Nova client that replays scripted turns, and Tier 3 catches only the regressions that require real Nova Sonic + real AgentCore Runtime + real cross-account KB Retrieve to surface. This tiering means a broken tool factory fails the pipeline in seconds; only the categorically-real-world failures (Nova Sonic transcription drift, cross-account KB access denial, cross-region Athena timeout) reach Tier 3. The smoke test suite complements evals by validating deployed-infrastructure surfaces that evals cannot exercise — `smoke-test-cross-account.py` verifies the Lake Formation grant is intact, `smoke-test-kb-retrieve.py` verifies the ADP KB `YULHRAUMNU` cross-account resource policy is intact, and `smoke-test-voice-multiturn.py` verifies the AgentCore Memory session-persistence path is intact. Every smoke test exits non-zero on failure, so `make deploy-staging` and the GitHub Actions `deploy-staging` job both fail loudly rather than silently completing with a broken runtime. CloudWatch Transaction Search plus X-Ray traces mean when a fleet_driver reports "the assistant hung on my second turn," an operator can correlate the specific session_id through the API Gateway → Lambda proxy → AgentCore Runtime → Nova Sonic bidi → cross-region Athena hop chain within a single CloudWatch console query rather than jumping across five service consoles. CDK-managed infrastructure means every environment (staging + prod) is deployed from the same TypeScript source with only stage-scoped config differences, so a config drift bug in staging is a bug in the code, not a divergence between environments.

### Why are you using these services to support operational excellence?

We selected these services to keep the mean time to detect (MTTD) low for regressions and the mean time to recovery (MTTR) low for incidents, both without operational toil that grows with the deployment size. The tiered evals pipeline was chosen over the alternative (post-hoc production monitoring + on-call rotation catching regressions) because Bedrock-first workloads have failure modes that traditional monitoring does not surface — a Nova Sonic transcription drift will not throw a Bedrock error, it will silently degrade the customer experience by mis-transcribing "P0420" as "P zero four twenty," and only a regression-suite comparing baseline conversation transcripts (Tier 3 `tier3_e2e.py` vs `evals/baselines/tier3.json`) can catch that class of degradation. Deploying via GitHub Actions with OIDC was chosen over the alternative (long-lived IAM access keys in a CI secrets store) because rotation of a leaked long-lived key is unbounded-cost operational toil, while OIDC federation means the CI role's trust policy defines the authorization boundary and there is no key to rotate. CloudWatch Transaction Search was chosen (requiring one-time account-level enable) over per-service log queries because AVX's request path crosses six service boundaries (browser → API Gateway → Lambda proxy → AgentCore Runtime → Bedrock model/Athena/KB) and correlating a single session_id across those six log groups by hand is expensive when a customer is waiting. The smoke test suite was chosen (over relying on evals alone) because evals validate agent behavior but not infrastructure — a session that would have passed a Tier 3 eval will still fail in production if the ADP KB resource policy was misconfigured on that specific deploy, and only a post-deploy smoke test against the live cross-account IAM boundary catches that class of failure before the first real user sees it. CDK-managed infrastructure was chosen so that the vast majority of "why is prod different from staging?" questions have a code diff for the answer rather than a snowflake environment to reconcile. Together, these choices make AVX safe to iterate on quickly — every commit to `main` goes through eval-gated auto-deploy to staging without a human bottleneck — while preserving the ability to root-cause a specific in-production incident within minutes rather than hours.

## Reliability

AVX v1 inherits reliability from AWS managed services without AVX-specific interventions:

- **Amazon Bedrock** (Sonnet 4.6 via cross-region inference profile, Nova Sonic v2, Knowledge Bases) — regional endpoints with automatic scaling; cross-region inference profiles route to alternate regions during regional stress.
- **Amazon Bedrock AgentCore Runtime** — managed scale-to-zero with automatic warm-start on invocation; two runtimes (`vsa_supervisor_text_staging`, `vsa_supervisor_bidi_staging`) can be updated independently.
- **AWS Lambda + API Gateway** — automatic scaling, multi-AZ by default.
- **Amazon S3** — 99.999999999% durability for Athena result buckets.
- **Amazon Bedrock AgentCore Memory** — regional managed service; graceful degradation is codified in tool factories: if Memory returns no records or KB is unavailable, tools return structured "not yet available" messages rather than failing the turn (see [`docs/ARCHITECTURE.md` — Graceful degradation](./docs/ARCHITECTURE.md#data-sources--v1-update)).

The Nova Sonic regional gap that this document previously recorded as a HIGH RISK is **closed**. Nova Sonic v2 is available in `us-west-2` (verified `ACTIVE` with bidirectional streaming, re-confirmed 2026-09-21), and staging invokes it in-region, so no cross-region path is exercised on voice sessions. The region is not a free knob: `NOVA_SONIC_REGION` must equal the execution-role region, because `InvokeModelWithBidirectionalStream` enforces an undocumented role-name allowlist and a cross-region call returns an empty-message `AccessDeniedException` that standard IAM diagnostics do not reveal (see [`docs/DEPLOYMENT.md`](./docs/DEPLOYMENT.md) § "Nova Sonic region — must equal execution-role region"). Treat it as a coupled pair — role region and Nova Sonic region move together or not at all.

## Performance Efficiency

AVX v1 inherits performance from AWS managed services and one design-time optimization:

- **AgentCore Memory with 15-minute TTL + lazy-refresh** eliminates per-turn cross-region Athena roundtrips for repeated tool calls within a session. The session-init cost (`persona_loader.load_persona` ~6–7 seconds cold) is a first-turn tax; every subsequent turn in the session reads from local Memory in the same region as the runtime.
- **Cross-region inference profile** for Sonnet 4.6 routes to whichever region has the fastest response, avoiding a hard binding to `us-west-2` capacity.
- **Serverless scale** at every request-path tier (API Gateway, Lambda, AgentCore Runtime) means AVX absorbs traffic bursts without capacity planning.
- **Persona-scoped tool dispatch** (per-persona filter selection in `bedrock:Retrieve` calls; see [`docs/ARCHITECTURE.md` — Tool Dispatch v1 Repointing](./docs/ARCHITECTURE.md#tool-dispatch--v1-repointing)) means each tool call retrieves only the KB chunks relevant to the current persona, not the full corpus.

At the v1 staging scale (~1,000 text turns/day + 100 voice sessions/day), no AVX-specific performance intervention is required beyond the Memory TTL. If customer scale exceeds ~10× staging, revisit: (a) Memory TTL sizing against observed session-length distribution, (b) Athena partition strategy for cross-region session-init queries, (c) Nova Sonic regional availability for voice-latency reduction.
